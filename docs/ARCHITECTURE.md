# Catalog Automation Platform — Architecture & Plan

**Status:** Draft for approval — nothing implemented yet
**Date:** 2026-08-12
**Scope:** Multi-tenant SaaS backend. Tenants define their own product taxonomy, capture a few
raw product photos, and the platform generates finished catalog imagery + marketing copy and
publishes it to their storefront and social channels. Sarees are the first vertical, not a
special case.

## 2. The hard problem (read this before the rest)

Almost everything below is standard SaaS engineering that is known to work. **One thing is not
known to work yet**, and it determines whether the product is viable:

> Given 3 close-up photos of a specific saree (bottom border, bunthi, blouse) and a reference
> template image, produce a catalog photo that is *commercially publishable* — where the
> generated saree is recognisably, faithfully **this** saree and not a plausible-looking
> different one.

This is image-conditioned generation with high fidelity constraints, not text-to-image. If the
model hallucinates a slightly different motif, the customer receives a product that doesn't
match the photo, and that is a refund and a trust problem, not a cosmetic one.

**D0 — Build the generation eval harness before the generation pipeline.**

Assemble a golden set of 20–30 real products with (a) the raw input photos, (b) a real
photographed catalog shot as ground truth. Score candidate models on:

- **Motif fidelity** — does the border/pallu/motif match the input at 100% crop? (human rating, 1–5)
- **Colour accuracy** — ΔE against the input swatch
- **Drape realism** — is the fabric physically plausible on a body
- **Template adherence** — does it match the reference composition/lighting/crop
- **Cost per accepted image** (including retries and rejects), **p95 latency**
- **Commercial licensing** of outputs, and whether the provider's ToS permits this use

Candidate families to evaluate (decide later, per your note):

1. **Multi-reference image editing models** — Gemini image models, `gpt-image-1`, FLUX Kontext.
   Fastest to integrate, fidelity varies by model.
2. **Specialised virtual try-on / garment-transfer models** (IDM-VTON, CatVTON class) — better
   garment fidelity, narrower to apparel, more infra to run.
3. **Self-hosted diffusion + ControlNet/IP-Adapter**, optionally a per-tenant LoRA — highest
   fidelity ceiling and lowest marginal cost, highest engineering cost.

The harness is ~1 week of work and is the cheapest possible way to avoid discovering in month
four that the core promise doesn't hold. Everything else in this document is designed so the
model behind it is a swappable adapter (D14).

> **Resolution — 2026-08-12.** Hand-tested against a real saree (4 input references, 3 scenes).
> **Nano Banana 2** clears the fidelity bar and is the chosen generation model. Two findings from
> the spike, both folded into the design:
>
> 1. **Text-scene templates outperform reference-image templates.** Passing a template *image*
>    made the model bleed the template garment's colour into the output. Describing the scene in
>    text and passing only the product references removed that failure mode entirely. So a
>    template is now **either** an analysed reference image **or** an authored text scene preset —
>    `catalog_templates.source_asset_id` becomes nullable and the analysis step is skipped for
>    authored presets. This also means a library of stock scene presets can ship to every new
>    tenant on day one, before they have sourced a single reference image.
> 2. **The prompt must not describe the product**, only the scene, placement, camera, light and
>    grade. Product identity comes entirely from the reference images; describing it in text
>    competes with them. The only product-adjacent instruction that earns its place is a drape
>    weight hint, which otherwise defaults to chiffon-like behaviour for every fabric.
>
> Still outstanding from D0: the formal golden set and the automated fidelity metric, which the QC
> agent (D20) needs regardless of model choice. The exact model id is pinned in provider config,
> not in code.

## 3. Multi-tenancy and data isolation

### D1 — Shared database, shared schema, `tenant_id` on every tenant-scoped row

**Decision.** One Postgres database. Every tenant-scoped table carries `tenant_id UUID NOT NULL`.

**Rationale.** Schema-per-tenant makes migrations O(tenants) and breaks Alembic's single-head
model; database-per-tenant multiplies connection pools and cost. Shared-schema is what scales to
thousands of tenants and is trivially reversible for a single large customer later (extract that
tenant's rows into a dedicated deployment).

**Consequences.** Isolation becomes a correctness obligation enforced at three independent
layers — D2, D3, and the repository layer.

### D2 — Composite foreign keys including `tenant_id` are the primary isolation guard

**Decision.** Every tenant-scoped table declares `PRIMARY KEY (id)` plus `UNIQUE (tenant_id, id)`.
Every foreign key between tenant-scoped tables is composite:

```sql
CREATE TABLE product_variants (
  id          UUID PRIMARY KEY,
  tenant_id   UUID NOT NULL REFERENCES tenants(id),
  product_id  UUID NOT NULL,
  ...
  UNIQUE (tenant_id, id),
  FOREIGN KEY (tenant_id, product_id) REFERENCES products (tenant_id, id) ON DELETE CASCADE
);
```

**Rationale.** This makes "variant of tenant A pointing at product of tenant B" *unrepresentable*.
RLS protects against a missing `WHERE` clause; composite FKs protect against a wrong `INSERT`.
They fail differently, which is the point.

### D3 — Row-Level Security as defence in depth, with two specific traps closed

**Decision.** `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY` on every
tenant-scoped table, with a policy on `current_setting('app.current_tenant', true)`. The
application connects as a **non-owner role** that has no `BYPASSRLS`.

Two failure modes that make RLS silently useless, both of which have burned teams:

1. **`FORCE` is required.** Table owners bypass their own RLS policies. Alembic runs as the owner;
   if tests also run as the owner, the entire suite passes with policies doing nothing.
2. **Must be `SET LOCAL`, inside the transaction.** With PgBouncer in transaction pooling mode,
   a plain `SET app.current_tenant` persists on the pooled server connection and leaks to the
   next tenant's request. `SET LOCAL` is scoped to the transaction and is the only safe form.

**Verification (a required test, not a nice-to-have):** a test that connects as the app role,
sets tenant A, and asserts that a direct query for a known tenant-B row returns zero rows. Add a
second test asserting the session variable does not survive a connection return to the pool.

### D4 — Identity: OIDC now, behind a port, with two planes of authority

**Decision.** Authentication is an `IdentityProvider` port. v1 implementation is OIDC
(Authlib) against Google Workspace / Microsoft Entra. Sessions are short-lived JWT access tokens
plus rotating refresh tokens stored server-side (revocable).

Two distinct planes:

- **Platform plane** — users whose verified email is on your company's domain **and** who hold an
  explicit `platform_admin` grant. Domain match alone is never sufficient. This plane manages
  tenants, global model configuration, quotas, and support impersonation (always audit-logged,
  always time-boxed).
- **Tenant plane** — `tenant_memberships(user_id, tenant_id, role)` with roles
  `owner | admin | catalog_manager | approver | viewer`. Permissions are checked as capabilities
  (`catalog.publish`, `template.manage`) rather than role names, so roles stay editable.

**Rationale.** Per-tenant enterprise SSO (SAML, SCIM) is a genuine time sink and a common reason
to adopt WorkOS/Auth0. Putting it behind a port now costs nothing and makes that a swap rather
than a rewrite.

## 4. Layering, and how it is enforced

### D5 — Six layers, with `infrastructure` importable only by the composition root

The layering you specified, made precise:

```
shared        Cross-cutting primitives with no domain meaning: ids, Result, base errors,
              clock protocol, pagination types. No I/O.

entities      Domain model. Entities, value objects, enums, domain events, invariants,
              domain exceptions. Pure Python — zero SQLAlchemy, zero FastAPI, zero I/O.

services      Domain + application services, and ALL PORTS (typing.Protocol): repositories,
              object storage, model providers, channel publishers, queue, unit of work.
              Logic that spans entities. Imports entities, shared.

features      Use cases. One class per use case (CreateProduct, RequestGeneration,
              ApproveCatalogImage). Owns the transaction boundary and emits domain events.
              Imports services, entities, shared.

agents        LLM-driven orchestrators (template analysis, copywriting, QC review). Deterministic
              Python control flow that calls model ports and validates structured output.
              Imports features, services, entities, shared.

api           FastAPI routers, request/response schemas, auth dependencies, error mapping.
              Imports agents, features, services, entities, shared.

infrastructure  Adapters IMPLEMENTING the ports: SQLAlchemy repositories, S3 client, provider
              SDKs, OAuth clients, queue driver. Imports entities/services for the Protocols
              it satisfies. ── Importable ONLY by `bootstrap`. ──

bootstrap     Composition root. Builds the app, wires concrete adapters to ports.
```

**The rule that makes the layering real:** ports are declared in `services`; implementations live
in `infrastructure`; nothing above `bootstrap` may import `infrastructure`. Without this,
"layered architecture" degrades into `features` importing SQLAlchemy directly within a month.

### D6 — Enforced by `import-linter` in CI from milestone 1

```ini
[importlinter]
root_package = app

[importlinter:contract:layers]
name = Layered architecture
type = layers
layers =
    app.api
    app.agents
    app.features
    app.services
    app.entities
    app.shared

[importlinter:contract:infra_isolation]
name = Infrastructure reachable only from the composition root
type = forbidden
source_modules =
    app.api
    app.agents
    app.features
    app.services
    app.entities
forbidden_modules = app.infrastructure

[importlinter:contract:pure_domain]
name = Entities are framework-free
type = forbidden
source_modules = app.entities
forbidden_modules = sqlalchemy, fastapi, redis, boto3, httpx
```

**Rationale.** An architecture rule that isn't a failing build is a comment. This goes in CI in
week one, when there are three modules and fixing violations is free.

### D7 — Domain entities are pure classes, mapped imperatively to SQLAlchemy

**Decision.** Domain entities are plain Python (dataclasses / attrs) in `entities`. SQLAlchemy
tables and the `registry.map_imperatively()` calls live in `infrastructure/persistence/mapping.py`.
There is one class per concept, not a domain class plus an ORM class plus a mapper.

**Alternatives rejected:**
- *Declarative ORM models used as entities* — fastest to write, but `entities` then imports
  SQLAlchemy and the "pure domain" claim is false. Workable if you forbid query logic on models,
  but the rule is unenforceable in review.
- *Separate ORM models + hand-written mappers* — pure, and roughly doubles the code with a
  mapping layer that rots.

**Consequences.** Async SQLAlchemy + lazy loading is a footgun; use explicit `selectinload` and
set `lazy="raise"` on relationships so an accidental lazy load fails loudly in tests rather than
silently N+1-ing in production.

**Reversibility:** high. If imperative mapping proves to be friction in month two, switching to
declarative models inside `entities` changes no call sites — only where the mapping is declared.

### D8 — Dependency injection via FastAPI `Depends` over Protocol types; no DI framework

**Decision.** `bootstrap/di.py` holds provider functions returning **port types**:

```python
def get_product_repository(session: SessionDep) -> ProductRepository:   # ProductRepository is a Protocol
    return SqlProductRepository(session)

ProductRepositoryDep = Annotated[ProductRepository, Depends(get_product_repository)]
```

Use cases take ports as constructor arguments and know nothing about FastAPI. Tests instantiate
them directly with fakes; API tests use `app.dependency_overrides`.

**Rationale.** `dependency-injector` works, but its `@inject` decorators and wiring calls put
container awareness into `features`, which is exactly the coupling the layering exists to
prevent. Plain `Depends` over Protocols gives the same testability with no library.

### D9 — Repository layer, transactions, and the tenant scope

**Decision.** A `UnitOfWork` port owns the transaction; use cases open exactly one. The session
dependency issues `SET LOCAL app.current_tenant` at transaction start from the authenticated
principal. Repositories take a `TenantId` explicitly in their signatures — never read it from a
global or a context var.

**Rationale.** Implicit ambient tenant context is how cross-tenant leaks happen in background
jobs, where there is no request. Explicit parameters make a missing tenant a type error.

## 5. Domain model

### D10 — Category taxonomy: adjacency list plus materialised path, with inheritance

```
categories
  id, tenant_id, parent_id NULL, path (ltree or text), depth,
  key, name, slug, description, position, is_active,
  current_spec_version, draft_spec_version,
  created_at, updated_at
```

Subcategories **inherit** their parent's attribute definitions, input slots, catalog slots and
variant axes, and may **add** to them or **override by key**. Resolution walks root→leaf,
last-writer-wins per key. So `Saree` defines `fabric`, `price`, the three input slots and the two
catalog slots; `Silk Saree` adds `zari_type` and an extra catalog slot without redefining
anything.

**Rationale.** Your example (Saree → Silk Saree, Fancy) is exactly the case where duplicating the
spec per leaf becomes unmaintainable at 20 subcategories.

### D11 — Custom fields: JSONB storage + definition table + semantic roles

**Decision.** Three parts working together:

```
attribute_definitions
  id, tenant_id, category_id (the category that OWNS the definition),
  key, label, help_text,
  data_type       (text | long_text | integer | decimal | money | boolean | date |
                   enum | multi_enum | url | image_ref | dimension),
  semantic_role   NULL | title | description | price | sku | brand | material | colour
  is_required, is_filterable, is_public, position,
  validation JSONB   -- {min, max, regex, maxLength, options:[...], unit}
  ui JSONB           -- {widget, placeholder, group, span}
  default_value JSONB,
  introduced_in_version, retired_in_version
```

- **Storage:** `products.attributes JSONB` + GIN index. One row per product, no EAV join
  explosion, no schema migration per tenant field.
- **Validation:** the definition set for a category compiles at runtime into a Pydantic model,
  cached by `(category_id, spec_version)`. Same model drives API validation and admin-UI form
  rendering, so they cannot drift.
- **Queryability — `semantic_role` is the important part.** Certain fields are structurally
  meaningful to *the platform*, not just the tenant: price must sort and filter, title must go in
  a social caption, colour must feed the generation prompt. A definition may be tagged with a
  role, and roles are projected into real typed columns (`products.price_amount`,
  `price_currency`, `title`, `sku`) maintained by the write path. Tenants keep full freedom to
  name and label their fields; the platform still gets a fast, indexable, generic hook.

**Alternatives rejected:** pure EAV (unusable query plans, painful ordering); one JSONB blob with
no definitions (no validation, no UI, no filtering); a real column per tenant field (DDL at
runtime — a non-starter for a shared schema).

**Interaction with D15.** Promoted columns are a projection, so retiring or re-roling the attribute
that backs one is a spec change that must enqueue a **reprojection job** over that category's
products. Until it completes, the projection is stale — so the promoted columns are treated as a
read-optimisation only. `products.attributes` JSONB is always the source of truth, and any
reconciliation resolves in its favour.

### D12 — Variants: generic axes, with `affects_imagery`

**Decision.** Do not hardcode "colour."

```
variant_axes          id, tenant_id, category_id, key, label, position,
                      affects_imagery BOOLEAN NOT NULL,
                      introduced_in_version, retired_in_version
variant_axis_values   id, tenant_id, axis_id, value, label, metadata JSONB   -- {hex:"#8B0000"}

product_variants      id, tenant_id, product_id, sku,
                      axis_values JSONB,          -- {"colour":"maroon","fabric":"tissue"}
                      attributes JSONB,           -- sparse overrides of the product's attributes
                      status, is_default, position
```

`affects_imagery` is what makes the generation pipeline generic: a **size** axis multiplies SKUs
but must not multiply generated images; a **colour** axis must. The generation fan-out is over
the distinct combinations of imagery-affecting axes only.

**Colour variants get their imagery two ways, both supported (A6):**

1. **Photographed** — the variant has its own input images. Variant-level input images override
   product-level ones per slot.
2. **Generated recolour** — the variant has no own inputs, so it falls back to the product's
   input images, and the colour axis value (plus its `metadata.hex`) is injected into the
   generation prompt as a recolour instruction.

The resolution rule is one line and covers both: *for input slot S on variant V, use V's image
for S if present, else the product's image for S.*

### D13 — Catalog specification: a category-level input pool, referenced by catalog slots

This is the heart of your requirement 7, and the modelling choice that makes it work.

```
input_image_slots                 -- the POOL, defined once per category
  id, tenant_id, category_id, key, label, description,
  capture_guidance, example_asset_id, is_required, position,
  introduced_in_version, retired_in_version

catalog_image_slots               -- what we PRODUCE
  id, tenant_id, category_id, key, label, description, position,
  aspect_ratio, target_width, target_height, is_required,
  introduced_in_version, retired_in_version

catalog_slot_input_requirements   -- the SHARING mechanism
  catalog_image_slot_id, input_image_slot_id,
  role,                 -- how this input is used here: "garment_body", "border_detail"
  is_required
```

For sarees: the category owns 3 input slots (bottom-border design, bunthi, blouse) and 2 catalog
slots (close-up, human-worn). The close-up slot requires {bottom-border, bunthi}; the human-worn
slot requires all three. **The photographer captures 3 images once**, and both catalog images draw
from that same pool, taking only what each needs — precisely the behaviour you described.

The admin UI can still present this as "define inputs while configuring this catalog image" —
inputs created inline are added to the category pool, and an existing pool slot can be attached to
a second catalog slot in one click. **UI affordance, pooled storage.** The alternative — inputs
owned by a catalog slot — makes sharing a duplication problem and would force re-photographing.

### D14 — Templates: analysed once, versioned, prompt placeholders validated at analysis time

```
catalog_templates
  id, tenant_id, catalog_image_slot_id, name, version, is_default, position,
  source_asset_id,
  status,                    -- see the state machine in §6
  analysis JSONB,            -- structured: composition, framing, camera, lighting, background,
                             --   pose, colour grading, crop, negative constraints
  prompt_template TEXT,      -- rendered prompt with {{...}} placeholders
  prompt_version, analysis_model, analysed_at, analysis_error,
  created_by, created_at
```

Per your requirement: on upload, a **vision model analyses the template** and produces both a
structured description and a reusable `prompt_template`. That template references runtime values
by placeholder:

```
{{input.bunthi}}  {{input.border_design}}  {{attr.fabric}}  {{variant.colour}}
```

**D14a — Validate placeholders at analysis time, not at generation time.** When analysis completes,
every `{{input.*}}` placeholder must resolve to an input slot declared in *this catalog slot's*
`catalog_slot_input_requirements`, and every `{{attr.*}}`/`{{variant.*}}` must resolve against the
category spec. A template that fails validation goes to `invalid` with a human-readable reason and
cannot be selected.

**Rationale.** Without this check, a bad placeholder surfaces as a generation failure hours later,
inside a batch, looking indistinguishable from a model error. This is a cheap check that removes an
entire class of confusing production incidents.

Templates are **immutable once analysed**. Editing produces a new version; existing generations
keep pointing at the version that produced them.

### D15 — Category spec versioning (the piece that prevents slow decay)

**Problem.** A tenant with 400 live products adds a fourth input slot, retires one, or reorders
catalog slots. Without versioning: the approval queue fills with images whose inputs no longer
exist, regeneration of an old product becomes impossible, and nobody can answer "what spec was
this product captured under?"

**Decision.** Slot/attribute/axis rows carry stable IDs plus `introduced_in_version` and
`retired_in_version` (soft, temporal versioning — rows are never hard-deleted). Publishing a spec
also writes an immutable snapshot:

```
category_spec_versions
  id, tenant_id, category_id, version INT, status (draft|published|archived),
  snapshot JSONB,        -- full resolved spec incl. inherited parent definitions
  change_summary JSONB, published_by, published_at
```

Products pin `category_spec_version_id` at creation. Generation always reads the pinned snapshot,
so a regeneration two years later reproduces what was originally intended.

**Change classes and their defined behaviour:**

| Change | Existing products |
|---|---|
| Add optional attribute / optional input slot / new catalog slot / new template | Auto-apply. New catalog slots appear as "not generated" with an offered backfill job. |
| Add **required** attribute or input slot | Products move to `needs_attention`; blocked from regeneration until filled. Bulk-fill UI provided. |
| Retire an input or catalog slot | Historical data retained; slot hidden from new capture; already-published images stay published unless explicitly retired. |
| Rename a `key` | **Not permitted.** Retire and add. (Labels and help text are editable in place — they carry no referential meaning.) |

**Consequences.** Every spec read goes through a `SpecResolver` service that takes
`(category_id, spec_version)`. Nothing reads the live slot tables directly except the spec editor.

### D16 — Settings: hierarchical resolution, with approval as the first consumer

```
settings   scope_type (platform|tenant|category|product), scope_id, key, value JSONB
```

Resolution is `platform default → tenant → category → product`, most specific wins. Your
configurable approval requirement is one key in this system rather than a bespoke flag:

- `approval.required` — bool
- `approval.required_channels` — e.g. `["instagram","facebook","pinterest"]` but not `"website"`,
  so a tenant can auto-publish to their own site while gating social
- `generation.auto_publish_on_approve`, `qc.min_confidence`, `publishing.schedule_strategy`

**Rationale.** Every SaaS grows 40 of these. Building the resolver once, generically, is cheaper
than 40 columns and makes per-category overrides free.

### D17 — Assets: content-addressed, presigned direct upload, derivatives on publish

```
assets   id, tenant_id, storage_key, sha256, mime, width, height, bytes,
         kind (template|input|generated|derivative), source, parent_asset_id NULL,
         meta JSONB, uploaded_by, created_at
         UNIQUE (tenant_id, sha256, kind)
```

Browsers upload directly to object storage via presigned PUT; the API only records metadata after
a verification callback (checks size, MIME sniff, dimensions, and an NSFW/abuse scan). SHA-256
addressing deduplicates the very common case of the same photo attached to several variants.

Per-channel renditions (aspect ratio and crop differ per platform) are **derivative assets**
generated at publish time from the approved master, with a `channel_render_specs` entry per
channel. Generating them at publish time rather than generation time means adding a channel later
doesn't require regenerating anything.

### D18 — Generation records: keep the attempt log and the current state separate

```
generation_requests
  id, tenant_id, product_id, variant_id, requested_by, status,
  spec_version_id, settings_snapshot JSONB, created_at, completed_at

generation_items          -- IMMUTABLE attempt log; one row per attempt
  id, tenant_id, request_id, catalog_image_slot_id, template_id, attempt_no,
  status, provider, model, model_params JSONB, seed,
  prompt_rendered TEXT, prompt_version,
  input_asset_ids UUID[], output_asset_id NULL,
  cost_micros, latency_ms, error_code, error_detail, created_at

catalog_images            -- CURRENT state, one row per (variant, catalog slot)
  id, tenant_id, variant_id, catalog_image_slot_id,
  asset_id, generation_item_id, status, is_primary,
  qc_result JSONB, approved_by, approved_at, rejection_reason,
  superseded_by NULL
  UNIQUE (tenant_id, variant_id, catalog_image_slot_id) WHERE superseded_by IS NULL
```

**On the partial unique index:** it permits exactly one live image per (variant, slot) while keeping
the full history. That makes regeneration a two-statement transaction — set `superseded_by` on the
existing live row **and** insert the new one, in the same transaction. Written any other way it is a
duplicate-key error in production, and the tempting "fix" is to drop the index, which silently
allows two live images for one slot.

**Both tables are needed.** `generation_items` is the immutable lineage record — which model,
which prompt version, which seed, what it cost, why it failed — which is what makes a result
reproducible, a regression diagnosable, and per-tenant cost attributable. `catalog_images` is the
mutable "what is live right now" with approval state. Collapsing them loses regeneration history
and muddles approval state with attempt state.

## 6. Pipelines: persisted state machines, queue executes steps

### D19 — Workflow state lives in Postgres; the queue only advances it

**Decision.** Each long-running process is a row with an explicit status, plus a `workflow_runs` /
`workflow_steps` pair recording progress. The task queue executes **one step** and commits a
transition. A reconciler poller sweeps for runs that are due, stuck, or retryable.

**Rationale.** The pipeline contains a step that waits for a human for an unbounded time
(approval). That is not a queue-able task — a worker cannot hold it, and a retry cannot resume it.
Once state is persisted and the queue is only a step executor, an ordinary queue is genuinely
sufficient, and a durable workflow engine stays a real escape hatch instead of an aspiration.

**Reliability primitives, all standard and all required:**
- **Transactional outbox** — domain events written in the same transaction as the state change; a
  relay publishes them. No "committed but never enqueued" gaps.
- **Idempotency keys** on every step that has an external side effect, written *before* the call.
- **Poison-message handling** — bounded retries with exponential backoff and jitter, then a dead
  state with the error preserved. Never infinite retry against a paid API.

**Queue choice: ARQ** (asyncio-native, Redis, small surface, fits an async FastAPI stack) behind a
`TaskQueue` port. Conservative alternative: **Celery** (larger ecosystem, mature ops tooling) if
you want beat/routing/Flower out of the box. Escape hatch: **Temporal**, if the saga complexity
outgrows a step-executor model. The port makes this a one-adapter change.

### Template lifecycle

```
uploaded ──▶ analysing ──▶ analysed ──▶ archived
                │              │
                ├──▶ analysis_failed (retryable)
                └──▶ invalid  (placeholder validation failed — D14a)
```
Only `analysed` templates are selectable for generation.

### 6.1 Input normalisation — the stage between capture and generation

Under A9, raw inputs arrive as phone photos: inconsistent white balance, cluttered backgrounds,
off-axis framing, wildly varying resolution. Feeding those straight to an image model degrades
fidelity in a way no prompt engineering recovers from — the D0 numbers are measured on
*normalised* inputs, so this stage is part of the fidelity result, not a cosmetic nicety.

```
captured ──▶ validating ──▶ normalising ──▶ ready
                  │                │
                  └──▶ rejected ◀───┘        (with a specific, actionable reason)
```

- **validating** — resolution floor, blur/focus score, exposure range, aspect sanity, MIME/dimension
  checks. Rejections must say *"too blurry — retake in better light"*, not *"invalid input"*; the
  person holding the phone is standing in the shop and can retake immediately.
- **normalising** — background removal/replacement, colour calibration (ideally against a reference
  card in frame), perspective correction, deskew, crop to the slot's expected framing, resize.
  Outputs a derivative asset; the original is always retained.

Normalised derivatives are what `generation_items.input_asset_ids` points at. Depth of processing
is a per-input-slot setting, since a flat fabric swatch and a hanging pallu need different
treatment.

### Product / variant lifecycle

```
draft ──▶ ready ──▶ generating ──▶ review ──▶ approved ──▶ publishing ──▶ published
             ▲                        │           ▲                          │
             │                        └──▶ rejected┘                         │
             └────────── needs_attention ◀── spec version change ────────────┘
```
`ready` requires all required attributes and all required input images present for the pinned spec
version. If `approval.required` is false, `review` is skipped and `generating → approved` is
automatic — see D20, which is what makes that safe.

### Generation

```
GenerationRequest:  queued ▶ running ▶ succeeded | partially_failed | failed | cancelled
GenerationItem:     pending ▶ running ▶ succeeded | failed(retry) ▶ dead
CatalogImage:       pending_qc ▶ qc_failed | pending_approval ▶ approved | rejected ▶ superseded
```
Fan-out is `distinct(imagery-affecting axis combinations) × required catalog slots × chosen template`.

### Publication

```
scheduled ──▶ dispatching ──▶ published
                   │
                   └──▶ failed(retry) ──▶ dead
```

### D20 — Automated QC is load-bearing when approval is disabled

**Decision.** Every generated image passes an automated QC gate *before* it reaches either the
approval queue or auto-publish:

- **Vision check against the slot spec** — is the expected subject present, correctly framed,
  matching the template's composition?
- **Fidelity check against the inputs** — does the motif/border match the source photos? (the D0
  metric, run automatically at a lower bar)
- **Colour delta** against the variant's declared colour
- **Artefact detection** — extra limbs, garbled text, duplicated motifs
- **Safety/brand-safety scan** before anything leaves for a public channel

Failures route to `qc_failed`, which triggers a bounded auto-retry (different seed, then a
different template) before surfacing to a human regardless of the approval setting.

**Rationale.** You asked for approval to be optional. When it is off, **there is no human between
a hallucinating image model and a customer's public Instagram account.** QC is the thing that makes
"approval off" a defensible product option rather than a liability, so it is a first-class
component, not a nice-to-have. A "QC failed — needs review" state must always exist even for
tenants who disabled approval.

## 7. Publishing

### D21 — Channels behind a port, with double-posting treated as the top-severity failure

```python
class ChannelPublisher(Protocol):
    capabilities: ChannelCapabilities        # aspect ratios, max media, caption length, video?
    async def validate(self, payload: PublishPayload) -> ValidationResult: ...
    async def publish(self, payload: PublishPayload, idempotency_key: str) -> PublishResult: ...
    async def fetch_metrics(self, external_id: str) -> ChannelMetrics: ...
```

Adapters: `website` (internal), `pinterest`, `instagram`, `facebook`; later `whatsapp_catalog`,
`google_merchant`, `shopify`.

```
social_accounts   id, tenant_id, provider, external_account_id, display_name,
                  credentials_encrypted BYTEA, encryption_key_id, scopes,
                  access_expires_at, refresh_expires_at, status, last_error

publications      id, tenant_id, variant_id, channel_id, content_draft_id,
                  idempotency_key UNIQUE, status, scheduled_at, published_at,
                  external_post_id, permalink, payload JSONB, attempts, last_error
```

**Double-posting is the highest-severity failure in this system** — publishing twice to a
customer's Instagram is worse than any data bug, is publicly visible, and cannot be undone. The
guards:

1. `idempotency_key` is generated and **committed before** the external call, with a unique index.
2. On retry, the adapter first *queries the provider* for a post carrying that key (or the
   recorded `external_post_id`) before re-attempting.
3. Per-account distributed rate limiting with a token bucket — platforms cap posts per
   account per day, and a burst of 40 queued publishes must not attempt to breach it.
4. A single-flight lock per `(account, variant)`.

**Scheduling** is a `due_at` column plus a poller — a task queue does not schedule reliably across
restarts and redeploys.

**Provider specifics are deliberately not written here.** Meta's Instagram Content Publishing
limits, long-lived token TTLs, the IG-Business-account-linked-to-a-Page requirement, and Pinterest
v5's board/pin model all drift, and a stale number in an architecture doc is worse than no number.
The *constraints* are architectural and stable — per-channel rate limits, a token refresh job
running well before expiry, encrypted credentials, and capability negotiation. Exact figures get
verified against provider docs at implementation time and encoded in the adapter's
`ChannelCapabilities`, where they are testable.

### D22 — Credentials: envelope encryption with rotation built in

Data-encryption keys wrap OAuth tokens (AES-256-GCM); DEKs are wrapped by a KMS master key.
`encryption_key_id` is stored per row so rotation is a background re-wrap rather than a migration.
Tokens are never logged, never returned by any API, and are redacted at the logging formatter.

### D23 — Copy generation and content drafts

```
content_drafts   id, tenant_id, variant_id, channel, locale,
                 title, body, hashtags TEXT[], cta, alt_text,
                 model, prompt_version, status, edited_by, created_at
```

The copywriting agent generates per-channel, per-locale copy from the product attributes and the
approved imagery (Instagram voice ≠ Pinterest SEO description ≠ website product copy). Copy is
subject to the **same approval gate** as imagery — an LLM inventing a fabric composition or a care
instruction is a consumer-protection problem, so brand rules and forbidden-claims lists are tenant
settings enforced by a validation pass, not just prompt instructions.

### D24 — Cost control: reserve quota atomically inside the enqueue transaction

```
usage_events        tenant_id, metric, quantity, unit_cost_micros, occurred_at, ref_type, ref_id
quota_reservations  tenant_id, period, metric, reserved, committed
```

Reservation happens **in the same transaction as the enqueue**, as a conditional update:

```sql
UPDATE quota_reservations
   SET reserved = reserved + :n
 WHERE tenant_id = :t AND period = :p AND metric = :m
   AND limit_value - reserved >= :n
RETURNING id;   -- zero rows ⇒ over quota, transaction rolls back, nothing enqueued
```

**Rationale.** Image generation is the dominant marginal cost. Check-then-act ("read the counter,
then enqueue") lets a burst of concurrent requests blow through a budget by an unbounded margin.
The conditional update is the only version that holds under concurrency. Reservations are committed
on success and released on terminal failure, so failed generations don't consume quota.

## 8. API surface

Versioned REST, OpenAPI-generated clients, `application/problem+json` errors, cursor pagination,
`Idempotency-Key` header honoured on all POSTs that cost money or publish.

```
/api/v1/platform/*    Operator console — tenants, plans, global model config, impersonation
/api/v1/admin/*       Tenant console — categories, spec editor, templates, products, variants,
                      generation, approval queue, channels, settings, usage

```

The existing React app consumes `/api/v1/public/*`. Its current `src/data/products.js` maps to
`GET /public/products` almost field-for-field; `categoryCopy` becomes category-level attributes;
`getRelated` becomes a server-side query. That frontend needs no restructuring, just a data-source
swap and a `?category=` filter route for the collections section that currently links to
non-existent anchors.

## 9. Non-functional

**Observability.** OpenTelemetry traces spanning API → queue → provider call (a generation is a
distributed transaction and is undebuggable without this). `structlog` JSON logs with
`tenant_id`/`request_id`/`trace_id` on every line. Sentry. Prometheus metrics: generation
success rate by model and by category, p95 latency, cost per accepted image, QC rejection rate,
approval turnaround, publish success by channel, queue depth and age.

**Per-generation lineage** — model, prompt version, seed, template version, spec version, inputs,
cost — is the single most valuable operational artefact in the system. It answers "why does this
image look wrong" and "why did last month cost triple."

**Testing.** pytest + pytest-asyncio. Postgres via testcontainers with the **real RLS policies and
the non-owner app role** (D3). In-memory fakes for every port, kept honest by contract test suites
run against both the fake and the real adapter. Golden-file tests for prompt rendering.
Provider calls recorded/replayed (VCR-style); a small nightly live-smoke suite against real
sandboxes. `ruff`, `mypy --strict`, `import-linter` in CI.

**Deployment.** Docker. Three process types: API, workers, poller/scheduler. Managed Postgres 16
with PITR. Redis/Valkey. S3-compatible object storage behind a CDN — Cloudflare R2 is worth
considering specifically for zero egress fees, since this product serves a lot of images.
Alembic migrations as a pre-deploy job, expand/contract only (never a destructive migration in the
same release as the code that stops using the column).

**Security.** Tenant isolation tests in CI (D3). Signed, short-lived URLs for private assets.
MIME sniffing and dimension limits on upload. Rate limiting per tenant and per IP. Audit log for
every state transition, approval, publish, credential change, and impersonation. Secrets from a
manager, never env files in the image.

## 12. Decisions that refine the plan, not gate it

The architecture stands as written. These two inputs would sharpen specific numbers in it:

1. **Shooting conditions.** A9 assumes phone photos and scopes §6.1 accordingly. If there is a
   studio setup with controlled lighting and a plain backdrop, §6.1 shrinks to validation only and
   M4 loses about half a week — and the D0 fidelity numbers improve independently of model choice.
2. **Expected scale in year 1** — tenants, products per tenant, images generated per month. This
   drives the cost model, the ARQ-vs-Celery call in D19, and whether read replicas belong in M9
   rather than "planned for" (A5).
